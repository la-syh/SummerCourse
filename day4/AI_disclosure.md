### 4. 讨论 tf-idf 和余弦相似度公式

根据课件，AI 建议使用对数词频：

​\[
w_{tf}(t,d)=
\begin{cases}
1+\log_{10}(tf_{t,d}), & tf_{t,d}>0,\\
0, & tf_{t,d}=0.
\end{cases}
\]

逆文档频率为：

​\[
idf_t=\log_{10}\left(\frac{N}{df_t}\right).
\]

文档中词项的 tf-idf 权重为：

​\[
w_{t,d}=\left(1+\log_{10}(tf_{t,d})\right)idf_t.
\]

文档向量长度为：

​\[
L_d=\sqrt{\sum_t w_{t,d}^2}.
\]

完整的余弦相似度为：

​\[
\cos(q,d)=
\frac{\sum_t w_{t,q}w_{t,d}}{L_qL_d}.
\]

AI 说明，课件示例在排序时只除以文档长度，是因为对固定查询而言 \(L_q\) 是常数，省略它不会改变排序。但为了返回真正的余弦相似度，最终实现应同时除以 \(L_q\) 和 \(L_d\)。

​\[

### 10. 明确查询时的稀疏余弦计算方式

我询问查询时是否需要对每个 HTML 网页分别计算一次余弦相似度。AI 说明，查询阶段不应再打开或解析任何 HTML，也不应遍历全部 15947 篇文档。索引构建阶段已将检索所需的 \(tf\)、\(df\)、idf、postings 和文档向量长度保存下来。

查询时只需进行以下操作：

1. 对查询分词，并计算查询词频和 tf-idf 权重；
2. 对每个查询词，只读取该词的 postings list；
3. 将这些 postings 中出现的 docID 作为候选文档；
4. 通过 `scores[docID]` 累加查询向量和文档向量的点积；
5. 只对 `scores` 中的候选文档使用已保存的文档长度进行余弦归一化；
6. 选取得分最高的 Top-K 结果。

因此，候选文档集合实际上是各查询词 postings list 中 docID 的并集。完全不包含查询词的文档点积为 0，不需要显式计算。

### 11. 检查初步的 tf-idf 查询实现

我实现了查询分词、候选文档得分累加、文档长度归一化和 Top-K 截取，并请 AI 检查当前 Day 4 代码。AI 确认当前查询已经只遍历查询词对应的 postings，没有重新打开 HTML，稀疏检索方向正确。

但 AI 指出，当前得分分子中的查询词权重和文档词权重都只使用了对数 \(tf\)，没有乘以该词的 idf；而已保存的文档长度却是使用 tf-idf 权重计算的。这会导致分子和分母使用不一致的向量表示，得到的数值不是 tf-idf 余弦相似度。

AI 建议对每个查询词使用相同的 idf 同时计算查询权重和文档权重，并累加查询向量长度：

​\[
w_{t,q}=\left(1+\log_{10}(tf_{t,q})\right)idf_t,
\]

​\[
w_{t,d}=\left(1+\log_{10}(tf_{t,d})\right)idf_t.
\]

得分最后应同时除以查询长度和文档长度。AI 还使用一个 idf 为 0 的模拟词项进行边界测试，确认当前代码会在文档长度为 0 时触发 `ZeroDivisionError`。因此，归一化前需要检查查询长度和文档长度是否为 0。

此外，AI 指出当前主程序仍固定使用 `remake=True`，正式索引生成后应改为 `False`；查询函数还应检查查询是否为字符串以及 \(k\) 是否为正整数。在 `conda ML` 环境中进行完整导入检查时，还发现该环境目前缺少 `jieba`。

### 12. 复查查询权重修正后的版本

### 14. 更正目标页面并检查重定向 URL 的记录

我随后更正说明，实际怀疑缺失的页面是 `https://gsai.ruc.edu.cn/addons/teacher/index.html`，而不是上一节检查的文继荣个人页。AI 重新检查了本地的 `url_index.jsonl`、`docID.jsonl` 和已保存 HTML，并联网核对了 URL 的跳转结果。

检查发现，精确 URL `https://gsai.ruc.edu.cn/addons/teacher/index.html` 的确没有出现在本地 URL 索引和 docID 映射中，但该页面的 HTML 内容已经抓取并保存在 `https://gsai.ruc.edu.cn` 对应的文件中，文件标题为“教师主页系统”，正文中也包含教师列表及各教师主页链接。

原因是访问种子 URL `https://gsai.ruc.edu.cn` 时，网站会经过一次 HTTP 重定向，最终到达 `https://gsai.ruc.edu.cn/addons/teacher/index.html`。当前爬虫的 `requests.get()` 会自动跟随重定向，但 `get_html()` 只返回响应正文；之后 `save_html(url, html)` 仍使用请求前的原始 URL 生成文件名和索引记录，没有保存最终响应 URL `response.url`。所以这是重定向后的规范 URL 没有被记录，不是页面内容没有下载。

AI 建议若要让 URL 索引准确反映最终地址，应让下载函数同时返回 HTML 与最终 URL，并在保存、去重和链接基址处理中统一考虑最终 URL。若作业只要求网页内容能够参与倒排索引和检索，当前该教师列表页的内容已经进入语料；若还要求 URL 映射准确，则需要再修正重定向处理逻辑。

### 15. 排查 HTTP 与 HTTPS 页面重复收录

我发现同一页面可能同时以 HTTP 和 HTTPS 两种地址进入语料，例如 `http://gsai.ruc.edu.cn/addons/video/video/play.html?id=2` 和对应的 HTTPS 地址。AI 检查本地 `url_index.jsonl` 与 `docID.jsonl` 后确认，这两个地址分别保存为不同文件，并分别获得 docID 3037 和 1635。按主机名、路径和查询参数相同而仅协议不同的条件统计，`gsai.ruc.edu.cn` 中共有 107 组此类记录。

AI 联网核对示例地址后确认，HTTP 地址会经过一次重定向，最终到达相同的 HTTPS 地址，而直接访问 HTTPS 地址不会发生重定向。因此这些记录在语义上是同一页面的重复抓取。出现重复的原因仍是爬虫只根据抓取前的 URL 字符串维护 `all_links`、生成文件名和写入 URL 索引，没有使用服务器响应中的最终 URL `response.url` 进行规范化和去重。

AI 不建议无条件把所有网站的 HTTP 地址改写成 HTTPS，因为并非所有主机都保证两种协议可用且内容等价。更稳妥的方案是让下载函数返回响应正文和最终 URL，将最终 URL 规范化后用于保存、解析相对链接和已保存页面去重，并维护原始 URL 到最终 URL 的重定向关系。对于现有数据，若清除重复记录，还需要重新生成连续的 docID 映射并重建 Day 4 倒排索引，不能只删除一个 HTML 文件或一行 URL 记录。

### 16. 检查下载函数返回最终 URL 后的配套修改

我将 `get_html()` 的成功返回值改为 `(response.content, response.url)`，并询问其他位置还需要如何调整。AI 检查当前代码后指出，调用处仍把整个返回值赋给 `html`，随后传给 `save_html()` 和 `ExtractHTML()`；若直接运行，写文件时会因为传入元组而不是字节串报错。

AI 建议在主循环中先判断下载结果是否为 `None`，再解包为 `html, final_url`，并统一使用 `final_url` 保存页面、解析相对链接和计算子链接优先级。同时应验证重定向后的主机名仍属于允许抓取的主机集合，避免 `requests` 自动跟随重定向后保存站外页面。

仅把最终 URL 加入现有 `all_links` 仍不足以可靠去重，因为 `all_links` 表示链接已经被发现或加入队列，并不表示页面已经成功下载。AI 建议另设 `saved_urls` 集合，从已有 `url_index.jsonl` 恢复，并在每次成功保存后更新。请求得到的 `final_url` 如果已经在 `saved_urls` 中，应跳过重复保存；从队列取出的 URL 如果已保存，也可以在发起请求前跳过。该修改只能防止以后新增重复，现有的 HTTP/HTTPS 重复记录仍需单独清理并重新生成 docID 和 Day 4 索引。

### 17. 复查重定向去重修改并安排后续步骤

我完成配套修改后询问下一步。AI 对当前 `Crawler.py` 进行了差异检查和静态编译检查。代码语法可以通过编译，但发现 `self.saved_urls = self.load_saved_urls()` 被放在 `self.url_index_file` 初始化之前；调用 `load_saved_urls()` 时访问该属性会触发 `AttributeError`，因此需要将该语句移动到 `url_index_file` 赋值之后。

AI 还指出，当前在下载失败、重定向到站外或最终 URL 已保存时直接执行 `continue`，会跳过循环末尾按 `save_interval` 执行的断点保存。建议调整控制流，使这些情况不绕过定期保存逻辑，或者把定期保存封装为不会被提前跳过的步骤。另外可以在发起请求前检查队列 URL 是否已经位于 `saved_urls`，从而减少不必要的重复请求。

AI 建议修正后先使用 HTTP/HTTPS 两个示例地址和独立的临时 HTML 目录、临时断点文件进行小规模测试，确认最终只写入一个 HTTPS URL，再决定如何处理正式数据。现有正式断点的 frontier 已为空，直接使用旧目录和旧断点运行不会自动删除或重新整理旧的重复数据；若需要完全干净的语料，应先备份旧结果，再重新抓取，之后重新生成 docID 并重建 Day 4 索引。

### 18. 确认重新抓取的启动方式

我确认备份完成后是否可以直接运行 `python -m day2.Crawler`。AI 说明，在前述初始化顺序和断点保存控制流问题修正后，应同时备份并移走原来的 `downloaded_html` 目录与 `crawler_checkpoint.json`，然后从 `hw` 目录进入 `conda ML` 环境运行该模块。这样爬虫会因找不到旧断点和旧 URL 索引而从种子 URL 重新开始，并创建新的抓取目录与索引。AI 同时建议先完成两网址的小规模测试，再开始耗时较长的完整抓取。

### 19. 分析姓名查询中个人主页未排第一的原因

我使用“赵鑫”进行查询时，两个视频页面排在赵鑫个人主页之前，因此询问排序原因。AI 从实际 Day 4 索引中提取了三篇文档的词频、idf、文档向量长度和余弦分数进行核对。

索引中“赵鑫”的文档频率为 173，idf 约为 1.963。视频 52 页面中该词的 (tf=1)，文档长度约为 4.943，单词查询余弦分数约为 0.397；视频 30 页面中 (tf=1)，文档长度约为 6.345，分数约为 0.309；个人主页中 (tf=2)，文档长度约为 9.659，分数约为 0.264。因此当前程序给出的前三名次序与实现的 tf-idf 余弦公式一致。

AI 解释，对于只有一个有效词项的查询，查询向量归一化后，排序主要取决于该词的文档权重占整篇文档向量长度的比例，而不是只比较词频。个人主页虽然出现两次“赵鑫”，但还包含 44 个索引词项以及 `batmanfly`、`aibox`、`gmail`、科研项目和学术论文等高权重词，文档向量长度明显更大；短视频页面的索引词更少，“赵鑫”在向量方向中的占比反而更高。

AI 进一步检查 HTML 结构发现，个人主页中的“赵鑫”分别出现在 `<title>` 和 `<h1>` 中，而视频页面中的姓名主要出现在 `<h3>` 中。当前实现把标题、一级至三级标题和段落分词直接合并后统一统计，没有为页面标题、一级标题或姓名主页设置字段权重。因此个人主页未排第一是标准词袋余弦模型的长度归一化结果，不表示代码计算错误。若希望姓名查询优先返回个人主页，需要在基础作业之外加入标题字段加权、精确标题匹配加分或其他排序特征。

### 20. 讨论标题、文档标题与正文的字段权重

我询问是否可以为 HTML 的 `title`、一级至三级标题和正文分别设置 5、2、1 的权重。AI 说明这种做法属于字段加权，可以作为基础 tf-idf 向量空间模型的扩展，但更准确的表述是将各字段中的词频乘以权重，而不是在最终检索分数上直接加固定分。

AI 建议可先分别对 `title_words`、`doctitle_words` 和 `body_words` 使用 `Counter`，再按 (5tf_{title}+2tf_{doctitle}+tf_{body}) 合成文档的加权词频，后续仍使用现有的对数 tf、idf 和余弦归一化流程。若同一词同时出现在页面标题和一级标题中，两部分贡献会相加，这正是字段加权希望表达的效果。

AI 同时提醒，这样保存的 `tf` 已经是加权词频而不是原始出现次数。如果作业要求明确保存真实词频，更严谨的做法是分别保存原始总词频和三个字段词频，再在评分阶段计算字段权重。无论采用哪种方式，文档向量长度必须按新的字段加权结果重新计算，否则分子和分母会使用不一致的表示。修改后需要以 `remake=True` 完整重建 Day 4 索引。

### 21. 复查字段加权实现

我完成字段加权代码后请 AI 检查。AI 确认当前实现分别统计 `title`、一级至三级标题和正文词频，保存原始 `tf` 与 `weighted_tf`，并在文档向量长度和查询文档权重两处统一使用 `weighted_tf`，整体计算逻辑一致，静态编译能够通过。

AI 指出当前实际权重为 3、2、1，而不是上一轮讨论的 5、2、1；若这是为了减弱标题权重而有意选择，则没有问题。当前磁盘中的旧索引 postings 仍然只有 `docID` 和 `tf`，但主程序仍设置 `remake=False`，因此直接查询会在读取 `weighted_tf` 时触发 `KeyError`。下一步应先将 `remake` 临时改为 `True` 完整重建索引，完成后再改回 `False`。

运行环境检查还发现，项目约定使用的 `conda ML` 环境目前缺少 `bs4`、`html5lib` 和 `jieba`，模块导入会首先因缺少 `bs4` 失败。因此在该环境中重建索引前，需要先补齐这些依赖，或者确认此前实际运行索引程序所使用的 Python 环境。
