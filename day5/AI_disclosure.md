### 4. 分析在线获取标题和摘要的问题

最初版本在每次查询得到 URL 后，使用 `requests.get()` 依次访问最多 20 个网页，并从返回的 HTML 中提取标题和摘要。AI 指出，这种实现虽然直观，但存在以下问题：

- 每次搜索都需要重新访问外部网站，响应速度受网络状态影响；
- 20 个网页依次请求，每个请求的超时时间为 10 秒，最坏情况下等待时间可能很长；
- 任何一个网页超时、拒绝访问或返回错误，都可能导致整个搜索结果页面报错；
- 外部网页内容可能发生变化，展示内容与建立索引时使用的本地网页版本不一致；
- 重复查询相同结果时会重复下载相同页面，浪费时间和网络资源。

AI 建议不要在查询请求中实时联网获取元数据，而是在索引或预处理阶段直接从 Day 2 已下载的本地 HTML 中提取标题和摘要，并保存为本地元数据文件。查询阶段只需按 URL 查表，不再访问外网。

### 5. 讨论本地网页元数据的保存格式

为了给出适合现有项目的方案，AI 检查了 `downloaded_html/docID.jsonl`、本地 HTML 文件布局和 Day 1 的 `ExtractHTML.py`。当前 `docID.jsonl` 的每条记录已经保存 `docID`、原始 URL 和本地 HTML 文件路径，因此可以直接作为离线元数据提取的输入。

AI 建议新增一个 JSONL 元数据文件，每行对应一篇文档，保存以下字段：

```json
{"docID": 0, "url": "https://example.com/", "title": "页面标题", "abstract": "页面摘要"}
```

选择 JSONL 的原因是它与现有 `docID.jsonl` 的格式一致，可以逐行处理，不需要在生成时将全部文档记录同时保存在内存中。查询程序启动时可以再将其加载为以 URL 为键的字典，因为当前 Day 4 的查询函数返回 URL 列表。

AI 建议将文件保存为 `inverted_index/page_metadata.jsonl`。该目录已经在 `.gitignore` 中，因此不会将本地网页的处理结果误提交到 Git，符合课件对中间结果的要求。

### 6. 讨论标题和摘要的提取规则

AI 建议标题按照以下优先级提取：

1. `citation_title`；
2. `og:title`；
3. `twitter:title`；
4. HTML 的 `<title>`；
5. 如果以上内容都不存在，则回退为页面 URL。

摘要按照以下优先级提取：

1. `citation_abstract`；
2. `description`；
3. `og:description`；
4. `twitter:description`；
5. 如果页面没有摘要元数据，则拼接段落文本，并截取正文前 200 个字符；
6. 如果仍然没有可用文本，则保存空摘要，在 Web UI 中显示“暂无摘要”。

AI 还建议将连续空白字符合并，避免网页中的换行和缩进直接出现在搜索结果中；单个网页解析失败时应记录失败信息并继续处理其他网页，而不是终止整个元数据生成过程。

### 11. 排查人名查询中的重复结果和短页面排名偏置

我发现搜索“毛佳昕”或“赵鑫”等人名时，排名靠前的结果中包含多个视频详情页、视频分类页和讲座页，其中若干 URL 实际展示相同或高度相似的内容。我认为这些结果挤占了 Top-K，降低了搜索结果的有效性和多样性，因此请 AI 排查原因。

AI 对照 `docID.jsonl`、本地 HTML、页面元数据和当前倒排索引进行了只读检查，并按现有 tf-idf 余弦计算方式重新计算了相关文档的得分。检查确认存在两类不同问题。

第一类是实际重复文档。例如，以下两个 URL 对应的本地 HTML 文件字节完全相同：

- `cate.html?cate_id=15&cate_name=...`；
- `cate.html?cate_id=15`。

此外，`cate.html?cate_id=15&page=1` 虽然原始 HTML 文件字节并不完全相同，但当前索引实际提取的标题、一级至三级标题和段落文本与前两个页面相同。因此，这三个页面在“毛佳昕”查询中的词频、加权词频和余弦得分完全一致，却分别占据三个结果位置。AI 还发现了教师列表页的 `/index.html` 变体和视频首页的 `/index.html` 变体等其他重复 URL。

第二类是当前余弦归一化对正文极短页面的排名偏置。视频详情页的页面标题是通用的“高瓴人工智能学院-视频中心”，正文段落为空，查询姓名只出现在一个标题元素中。由于页面中被索引的词项很少，文档向量长度较短，余弦归一化后反而得到很高的相似度。

AI 重新计算“毛佳昕”的排名后发现：视频详情页 `play.html?id=69` 得分约为 0.490，教师主页得分约为 0.364，讲座详情页得分约为 0.168；三个重复分类页得分均约为 0.153。对于“赵鑫”，排名第一和第三的结果也是正文很短的视频详情页，而教师主页排名第二。这说明问题不仅是网页内容重复，也包括短文档被余弦相似度过度奖励。

AI 建议按以下顺序改进：

1. 在元数据预处理阶段，根据用于检索的标题、各级标题和正文生成内容指纹；
2. 查询时先取比最终 Top-20 更大的候选集，再按内容指纹去除完全重复结果；
3. 对 URL 做谨慎的规范化，删除仅用于显示的参数，将 `page=1` 与没有 page 参数的首页视为同一分页页面，但保留 `id`、`cate_id` 等具有实际语义的参数；
4. 在基础 tf-idf 得分上增加查询词命中 HTML `<title>` 的加分，使“毛佳昕-教师系统”“赵鑫-教师系统”等明确主题页面优先于只在列表标题中出现姓名的页面；
5. 对分类页、列表页等聚合页面适当降权，避免列表中的一次姓名出现压过个人主页；
6. 如需进一步把视频页和对应讲座新闻聚合，可使用 SimHash、文本 shingles 或最大边际相关性重排，对高度相似结果进行聚类或多样性惩罚；
7. 保留原有自动评测所需的 URL 返回接口，在其内部增加候选集去重和重排，避免破坏接口形式。

AI 建议先实施“内容指纹去重 + 标题命中加分”，因为这两项改动较小、容易解释，也能直接解决当前最明显的问题；多样性重排可以作为后续扩展功能。此次仅进行了原因分析和方案讨论，AI 没有修改当前检索代码。

### 12. 排查每条搜索结果连续显示两次的问题

我按照上一轮建议加入内容指纹、URL 规范化、候选集去重和标题命中优先级后，搜索“高瓴”时发现页面虽然显示 20 条结果，但每个 URL 都连续出现两次，而且多个视频页面显示相同的站点级摘要。我将实际页面输出反馈给 AI，请其继续定位。

AI 检查当前 `main.py` 后发现，`search()` 在同一次候选循环中执行了两次 `results.append(url)`。第一次追加发生在记录规范 URL 之后，第二次追加发生在记录内容指纹之后。因此，每个通过去重检查的 URL 都会被连续加入结果列表两次；当列表长度达到 20 时，实际只处理了 10 个不同候选。这与页面上“同一结果恰好连续出现两次”的现象完全一致。

AI 同时统计了 `docID.jsonl`，确认当前共有 15886 条记录和 15886 个不同 URL，不存在相同 URL 被保存两次的情况。因此，本次成对重复不是爬虫或倒排索引造成的，而是 Day 5 结果组装中的重复追加。

AI 建议只保留一次 `results.append(url)`，并在追加后记录内容指纹，再根据去重后的结果数量判断是否达到 (k)。当前 URL 规范化和内容指纹集合的总体思路可以保留。

对于不同视频页显示相同摘要的问题，AI 检查发现这些页面的 meta description 都是“新首页_中国人民大学高瓴人工智能学院”一类站点级通用文案。当前元数据生成程序只要发现 description 就优先使用它，因此不会回退到视频页面的具体标题。AI 建议将通用站点描述视为无效摘要；视频页正文段落为空时，可使用第一个 `h1` 至 `h3` 标题作为摘要或展示标题。这个问题与结果成对重复相互独立，需要分别修正并重新生成 `page_metadata.jsonl`。

AI 进一步指出，搜索“高瓴”时大量不同视频页排在前面还有第三个原因：当前代码使用布尔条件将“页面标题包含完整查询词”的全部候选整体移动到前面，而所有视频页的通用标题“高瓴人工智能学院-视频中心”都包含“高瓴”。因此标题优先规则会把整批视频页一起置顶。不同视频 `id` 的标题元素和内容指纹并不相同，精确内容去重不会删除它们；这属于同一路径类型结果过多造成的多样性问题，而不是完全重复文档。

AI 建议不要对通用站点标题使用强制置顶规则，可以先移除该二值排序，或先剥离站点名称和通用模板文字后再判断查询是否命中页面特有标题。为保证结果多样性，还可以按 hostname 和 URL path 建立结果族，例如将所有 `/addons/video/video/play.html?id=...` 归为同一族，在 Top-20 中最多保留两条；视频分类页族最多保留一条。搜索时仍从较大的候选集合中继续选择其他类型页面，以补足 20 条结果。

本轮中 AI 进行了代码审查、数据计数和原因说明，没有直接修改 `main.py` 或元数据生成代码。

### 13. 实现查询词高亮显示

我希望像 Google 搜索结果一样，在结果标题和摘要中将与查询匹配的部分标红显示，因此请 AI 直接协助实现该功能。本轮中，AI 修改了 `day5/main.py`、`templates/res.html` 和 `static/style.css`。

AI 在 Flask 中注册了名为 `highlight` 的 Jinja 模板过滤器。过滤器将查询内容按空白拆分为一个或多个关键词，使用 `re.escape()` 处理关键词中的正则表达式特殊字符，并采用不区分英文字母大小写的匹配方式。为避免较短关键词抢先匹配较长关键词，过滤器先按长度从长到短排列去重后的查询词。

高亮实现没有直接对网页原始标题和摘要使用 `safe`。AI 使用 MarkupSafe 的 `escape()` 分别转义普通文本和匹配文本，仅由程序生成的 `<mark class="query-highlight">` 标签被保留为 HTML，从而避免本地网页标题或摘要中的 HTML 内容被浏览器当作可执行标签渲染。

结果页模板中的标题和摘要分别改为通过 `highlight` 过滤器渲染，URL 保持原样，不进行高亮。CSS 中新增 `.query-highlight` 样式，使用红色、透明背景和粗体显示命中部分。该功能支持中文完整查询，例如“毛佳昕”和“高瓴”，也支持以空格分隔的多个查询词。

本次高亮功能由 AI 根据我的明确要求直接写入项目文件。我负责检查最终实现、运行效果和提交内容。
